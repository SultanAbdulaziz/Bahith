# videoIR Backend: API Documentation

videoIR is a search engine for the inside of videos. Users upload videos, the backend transcribes them and splits each transcript into 15-second **documents**, and users can then search (BM25 or Boolean) or ask questions (an AI chat with cited sources) and jump straight to the right moment in the video.

All endpoints are served under `/api`. Interactive docs are generated by FastAPI at `http://localhost:8000/docs`.

---

## Running locally

```bash
# 1. Postgres (from the repository root)
docker compose up -d db

# 2. Environment + migrations (from src/backend/)
cd src/backend
source ../../.venv/bin/activate
set -a; source ../../.env; set +a
alembic -c db/alembic.ini upgrade head

# 3. API (terminal 1)
uvicorn src.main:app --reload

# 4. Worker, which transcribes uploaded videos (terminal 2, same environment setup)
python -m src.worker.sweep
```

Without the worker running, uploaded videos stay `pending`.

## Conventions

### Authentication
- Sessions use **`HttpOnly` cookies** set by the backend. Clients never handle tokens directly.
- Browsers must send cookies on every request: `fetch(url, { credentials: "include" })`.
- **`access_token`**: valid **15 minutes**, sent to every path.
- **`refresh_token`**: valid **14 days**, only sent to `/api/auth/*`. It is **single-use and rotated** on every refresh. Reusing an old one ends the session.
- When a request returns `401`, call `POST /api/auth/refresh` **once** and retry. If that also returns `401`, the session is over. Never send two refresh requests at the same time.

### Errors
All errors return JSON `{"detail": "..."}`.

| Status | Meaning |
|---|---|
| `400` | Invalid file request (unsupported type, file not found or not owned by the caller) |
| `401` | Not logged in, expired/invalid session, or an auth error (wrong password, email taken, ...) |
| `422` | Request validation failed (missing or invalid fields/parameters) |
| `429` | Chat: too many requests to the AI service right now |
| `502` | Chat: the AI service did not respond |

Users only ever see their own files, documents and search results.

### Auth

#### `POST /api/auth/guest`
Creates a guest user and a session. A guest can use every feature.
- **Body:** none
- **Response:** `204`, sets the auth cookies.

#### `POST /api/auth/register`
```json
{"email": "user@example.com", "password": "at least 8 characters", "name": "optional"}
```
- If the caller is currently a **guest**, that guest is **upgraded in place**: same user ID, and all their files are kept. Otherwise a new account is created.
- The email is trimmed and lowercased. The password must be 8 characters to 72 bytes.
- **Response:** `204`, sets the auth cookies.
- **Errors:** `401` `"email already registered"`, `"password must be at least 8 characters"`, `"password too long"`.

#### `POST /api/auth/login`
```json
{"email": "user@example.com", "password": "..."}
```
- **Response:** `200` (empty body), sets the auth cookies.
- **Errors:** `401` `"incorrect email or password"` (the same message whether or not the email exists).

#### `POST /api/auth/refresh`
Uses the `refresh_token` cookie.
- **Body:** none
- **Response:** `200` (empty body), sets new auth cookies.
- **Errors:** `401` `"invalid refresh token"` (missing, expired, revoked, or reused).

#### `POST /api/auth/logout`
- **Body:** none
- **Response:** `204`. Deletes the session and clears both cookies.

#### `GET /api/auth/me`
```json
200 {
  "id": "0192f3a1-...",
  "email": "user@example.com",
  "name": "Jane",
  "is_guest": false,
  "is_email_verified": false
}
```
Guests have `email: null` and `is_guest: true`. Use this on app load: `200` means a session exists, `401` means none.

### Files

Uploads go **straight from the client to R2** with a presigned URL. The file never passes through the backend.

```
1. POST /api/files                    → {file_id, upload_url}
2. PUT  upload_url  (the file bytes)  → 200, directly to R2
3. POST /api/files/{file_id}/complete → the worker picks it up
4. GET  /api/files  (poll)            → until status is "done"
```

#### `POST /api/files`
```json
{"content_type": "video/mp4"}
```
- `content_type` is the file's MIME type. Only `video/*` is accepted.
- **Response:**
  ```json
  201 {"success": true, "file_id": "0192f3a1-...", "upload_url": "https://<account>.r2.cloudflarestorage.com/...?X-Amz-Signature=..."}
  ```
- **Errors:** `400` `"File type not supported"`.

#### Uploading to R2 (not a backend endpoint)
```
PUT {upload_url}
Content-Type: <exactly the content_type sent to POST /api/files>
<raw file bytes>
```
- The `Content-Type` must match exactly, or R2 rejects the upload with `403`.
- The URL expires after **15 minutes**.
- Don't send credentials with this request.

#### `POST /api/files/{file_id}/complete`
- Moves the file from `uploading` to `pending`, so the worker processes it.
- **Response:** `204`.
- **Errors:** `400` `"file not found"`: unknown ID, not the caller's file, or already completed.

#### `GET /api/files`
The caller's files, newest first.
```json
200 [
  {
    "id": "0192f3a1-...",
    "type": "video/mp4",
    "status": "done",
    "meta": {"duration": 52.2},
    "error": null,
    "created_at": "2026-10-20T10:00:00+00:00"
  }
]
```

| `status` | Meaning |
|---|---|
| `uploading` | Upload URL issued, not confirmed yet |
| `pending` | Waiting for the worker |
| `processing` | Being transcribed |
| `done` | Searchable. `meta.duration` holds the length in seconds |
| `failed` | Processing failed. Retried automatically up to 3 times; `error` holds the reason |

#### `GET /api/files/{file_id}/url`
- **Response:** `200` with a JSON **string**: a presigned playback URL, valid for **1 hour**.
  ```json
  "https://<account>.r2.cloudflarestorage.com/files/video/0192f3a1-...?X-Amz-Signature=..."
  ```
- Use it directly as a video source. Browsers stream it with range requests, so seeking works.
- **Errors:** `400` `"file not found"`.

#### `DELETE /api/files/{file_id}`
- Deletes the object from R2 and the file with its documents from the database. It disappears from the file list and from search.
- **Response:** `204`.
- **Errors:** `400` `"file not found"`.

### Search

#### `GET /api/search?query=...&mode=bm25&k=10`

| Parameter | Type | Default | Notes |
|---|---|---|---|
| `query` | string | required | |
| `mode` | `bm25` or `boolean` | `bm25` | |
| `k` | integer 1–100 | `10` | Maximum results returned |

- **`bm25`:** ranked by relevance, best first.
- **`boolean`:** exact matching, in document order, with `score: null`. A **space means OR**, `&` means AND, and AND binds tighter: `lecture exam&date` = *lecture* OR (*exam* AND *date*).
- Matching is case-insensitive, ignores punctuation, and has no stemming ("searching" does not match "search").

```json
200 {
  "query": "gatekeepers",
  "mode": "bm25",
  "total": 1,
  "results": [
    {
      "file_id": "0192f3a1-...",
      "type": "video/mp4",
      "text": "What brings you to the land of the gatekeepers?",
      "meta": {"start": 0.0, "end": 15.0},
      "score": 1.05
    }
  ]
}
```
- `total` is the number of **all** matches. `results` holds at most `k` of them.
- `meta.start` and `meta.end` are seconds into the video. Seek the player to `meta.start` to jump to the result.
- Only `done` files have documents, so videos still processing don't appear yet.

### Chat

#### `POST /api/chat`
Answers a question using **only** the user's video transcripts, with numbered citations.

```json
{
  "question": "What is the hunter looking for?",
  "history": [
    {"role": "user", "content": "previous question"},
    {"role": "assistant", "content": "previous answer"}
  ],
  "file_id": null,
  "k": 5
}
```

| Field | Type | Default | Notes |
|---|---|---|---|
| `question` | string | required | Trimmed, 2–500 characters |
| `history` | list of `{role, content}` | `[]` | `role` is `user` or `assistant`; up to 20 messages, content up to 4000 characters. Only the last 6 are sent to the model |
| `file_id` | UUID or `null` | `null` | Restrict the answer to one video. `null` searches all the user's `done` videos |
| `k` | integer 1–10 | `5` | Number of transcript excerpts given to the model |

The relevant excerpts are found with BM25, using the question plus the previous user message, so follow-up questions keep their context.

```json
200 {
  "answer": "He is searching for someone [2], on a dangerous quest as a lone hunter [3].",
  "sources": [
    {
      "number": 2,
      "file_id": "0192f3a1-...",
      "start": 15.0,
      "end": 30.0,
      "text": "I'm searching for someone.",
      "score": 0.957,
      "video_url": "https://<account>.r2.cloudflarestorage.com/...?X-Amz-Signature=..."
    }
  ]
}
```
- Citations like `[2]` in `answer` refer to the source with the same `number`.
- `video_url` is a presigned playback URL (1 hour). Seek to `start` to show the cited moment.
- The answer is written in the language of the question.
- If nothing relevant is found, `answer` says so and `sources` is `[]`.
- **Errors:** `429` `"too many questions right now, please wait a moment and try again"`, `502` `"the AI service is not responding, please try again"`, `422` for invalid fields.

### Demo (public)

#### `GET /api/demo?query=...&mode=bm25&k=10`
Lets visitors try search **without logging in**, on a fixed demo video (the oldest `done` video of the user set in `DEMO_USER_ID`).

| Parameter | Type | Default | Notes |
|---|---|---|---|
| `query` | string | `""` | Empty returns no results, but still returns the video URL |
| `mode` | `bm25` or `boolean` | `bm25` | |
| `k` | integer 1–100 | `10` | |

```json
200 {
  "query": "gatekeepers",
  "mode": "bm25",
  "total": 1,
  "results": [
    {"file_id": "0192f3a1-...", "type": "video/mp4", "text": "...", "meta": {"start": 0.0, "end": 15.0}, "score": 1.05}
  ],
  "file_id": "0192f3a1-...",
  "video_url": "https://<account>.r2.cloudflarestorage.com/...?X-Amz-Signature=..."
}
```
- Results use the same format as `/api/search`. `video_url` is the demo video's playback URL (1 hour).
- **Errors:** `400` `"demo video not found"` if the demo user has no processed video.

## How processing works

1. `POST /api/files` creates the file row with status `uploading` and returns a presigned PUT URL.
2. The client uploads to R2 and calls `/complete`, which sets the status to `pending`.
3. The worker (`python -m src.worker.sweep`) claims pending files one at a time, using `FOR UPDATE SKIP LOCKED`, so several workers can run safely.
4. It streams the audio from R2 with ffmpeg in 10-minute chunks, transcribes each with Groq Whisper (`whisper-large-v3-turbo`), and groups the transcript into 15-second documents stored with `{start, end}` metadata.
5. The file becomes `done`. Failures are retried up to 3 times, and files stuck in `processing` for over an hour are picked up again.

Search builds a per-user inverted index in memory from the user's documents, caches it, and rebuilds it only when those documents change.
